# CottenRouter v1.2.19

Installed backends can now be updated independently of CottenRouter:

```bash
sudo cottenrouter update --project cottendns
```

In the TUI select an installed project and press **U**. Enter edits settings;
U fetches the project's current upstream installer and keeps the managed
integration settings. Upstream releases do not require a new router build.

CottenDNS updates resolve the latest published `WhiteDNS/CottenDNS` release
at operation time, pass the exact tag to its fresh installer, and verify the
systemd executable's reported version. Updates fail if release resolution or
version verification fails instead of silently using an old version.

The native installer's modification-time selection could choose an older
executable left in the directory. CottenRouter now selects the executable for
the exact resolved release. Verified release tags are recorded and shown in
the TUI; the previous service unit is restored if installation fails.

The old `TaJirax/cottenDNS` fork still publishes September 26, while the current
WhiteDNS repository publishes October 8. This fixes the update behavior behind
[issue #2](https://github.com/TaJirax/CottenRouter/issues/2).
The config's `CONFIG_VERSION` describes its preserved template, not the binary
version. CottenMax remains part of the single CottenDNS backend.

Validation on Ubuntu 24.04/WSL2 upgraded an actual September 26 service to
`v2026.10.08.163633-1f3cc52`, deliberately leaving the old executable newer by
mtime. The key, backend config, router config and router binary retained their
checksums. Unit, race, static-analysis and CLI/TUI checks cover release refresh,
stale-version rejection and integration preservation.
